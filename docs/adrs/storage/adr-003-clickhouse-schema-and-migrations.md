# ADR-003: Schema Owned by Versioned Migrations, Not by the Collector Exporter

* **Status**: Accepted
* **Date**: 2026-09-26
* **Deciders**: MemTrace Core Team

## Context and Problem Statement

The ClickHouse exporter of the OTel Collector can create its own tables (`create_schema: true`, default table `otel_traces`). The first design also defined a hand-written table (`otel_spans`), so there were two sources of truth and the Collector would have written to a different table than the one queried. The roadmap also requires **versioned migrations**.

## Decision Outcome

1. The schema is defined **only** in `migrations/clickhouse/NNN_*.sql`.
2. The Collector runs with an explicit `traces_table_name: otel_traces` (leaving table creation to the migration job).
3. The table `memtrace.otel_traces` replicates the column layout the exporter (`otelcol-contrib` 0.96.0) inserts, so writes stay compatible.
4. A Kubernetes Job (`clickhouse-migrate`) applies pending files in order and records each in `memtrace.schema_migrations`. It is idempotent and can be re-run (the Job is deleted before re-applying, since Jobs are immutable). The migration ConfigMap is generated by kustomize (`kubectl apply -k .`) from the SQL files, so there is no manual step.
5. Applied migrations are never edited; changes go into a new file.
6. Retention (30-day TTL) is defined only in the migration, not in the exporter.
7. Query-oriented design:
   - `ORDER BY (ServiceName, SpanName, toDateTime(Timestamp))` for per-agent aggregations.
   - Auxiliary table `otel_traces_trace_id_ts` (fed by a materialized view) to locate a trace by `TraceId` without scanning the main table.
   - Daily partitions plus `ttl_only_drop_parts = 1` to purge by dropping whole parts.

## Consequences

- **Positive**: single source of truth; schema evolves under review; the query API (piece 4) can rely on a known layout.
- **Negative**:
  - Upgrading the Collector requires checking exporter/schema compatibility. The initial column layout is unverified against a running 0.96.0 exporter and must be validated with the first real trace (see design doc, section 3).
  - Root-span listing uses `ParentSpanId = ''` within a time range; a projection or materialized view will be added by a later migration if volume requires it.
  - A hand-rolled migration Job is minimal; a dedicated migration tool can replace it later without changing the file convention.
