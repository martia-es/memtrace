# ADR-065: Code Revision on Traces and Evaluations

* **Status**: Proposed
* **Date**: 2026-10-07
* **Deciders**: MemTrace Core Team
* **Related**: [ADR-064](../governance/adr-064-ci-triggered-deployments-with-evaluation-gate.md), [ADR-006](../sdk/adr-006-python-sdk-design.md), [ADR-034](../README.md#retired-adrs)

## Context and Problem Statement

We want to know **which version of the code produced each trace**, and to tie the commit evaluated offline to the commit that runs in production. MemTrace cannot add metadata to traces at deploy time: traces are generated by the running application. The commit has to travel *inside* the application, automatically, with no manual linking.

## Decision Outcome

### The CI injects the commit, the SDK reads it

- The CI of the agent's repo passes the commit SHA at build time (`--build-arg GIT_SHA=<sha>`, `ENV GIT_SHA=$GIT_SHA` in the Dockerfile). The value changes on every build because the CI fills it with the commit it is building; when MemTrace triggers the deploy (ADR-064), it passes the exact SHA it validated.
- At startup the SDK resolves the revision, first match wins: `MEMTRACE_GIT_SHA` → `GIT_SHA` → platform variables (`GITHUB_SHA`, `CI_COMMIT_SHA`, `VERCEL_GIT_COMMIT_SHA`, `RENDER_GIT_COMMIT`, `HEROKU_SLUG_COMMIT`) → `git rev-parse HEAD` when running inside a repository (local development).
- It is set as an OpenTelemetry **resource attribute** on every trace: `vcs.repository.ref.revision` (the OTel semantic convention), plus `memtrace.revision.dirty` when the working tree has uncommitted changes (only detectable in the `git` fallback).
- No revision found → traces are sent without it; the UI shows "unknown version". The SDK never fails because of it.

### Evaluations carry the same revision

`run_experiment()` resolves the revision with the same function and stores it on the run (`revision`, `revision_dirty`). Evaluations launched by the CI on push/PR get the SHA automatically; local runs use `git rev-parse HEAD` and are marked dirty when applicable, so they never satisfy the deploy gate of ADR-064.

### Storage and queries

**Phase 1 (done)**: the SDK sends the attribute and ClickHouse already keeps it in `ResourceAttributes['vcs.repository.ref.revision']`, so no migration was needed to store it. **Phase 2a (done for traces)**: migration `clickhouse/011_revision.sql` adds the materialized `Revision` column and its index; `GET /traces` accepts `revision` (full SHA or prefix) and returns it on each trace and on the trace detail; the dashboard shows the short SHA in the trace list and detail. **Also done (2a complete)**: `revision` filter on conversations and spans; evaluation runs record the commit (`dataset_runs.revision` / `revision_dirty`, migration `postgres/030_dataset_run_revision.sql`, sent by `MemTraceResultsSink`) and return it in every run DTO; the dashboard links the short SHA to the commit in the repository (trace detail, traces list, run detail, runs table, `CommitLink`), has a *Code version* filter in Conversations (a dropdown of the commits seen in the range, with trace counts, from `GET /revisions`, instead of typing a hash) and shows the CI snippet (Dockerfile + build step per provider) on the assistant page (the `eval.item` traces already carry it as spans).

- ClickHouse: `Revision` column (LowCardinality String) materialized from the resource attribute on traces and on eval tables, with a skip index for filtering. Migration pending.
- API: `revision` filter on trace/conversation/eval-run listings and on aggregates, so two commits can be compared (cost, latency, scores, feedback).
- Dashboard: short SHA (linked to the repo commit when `repo_url` is known) in trace/run detail, and a revision filter.

### One-time setup per repo

Two lines (build-arg in the workflow, `ARG/ENV` in the Dockerfile). MemTrace shows a ready-to-copy snippet and a sample workflow on the assistant card; opening a pull request with the change is a later option. Platforms that already expose the commit need nothing.

### Known limit: the commit is not the whole version

Prompts managed outside the repo, model/provider changes, env vars and RAG data can change behavior at the same SHA. Follow-up: optional `memtrace.config_hash` resource attribute, computed by the SDK from the settings the user declares.

## Consequences

* (+) Every trace and evaluation is tied to a code version, with zero manual linking.
* (+) Deployed commit vs. evaluated commit can be verified, and drift detected (traces with a different revision than the last recorded deploy).
* (+) Uses an OTel standard attribute, readable by any backend.
* (−) One-time CI change per repo; without it the version is unknown.
* (−) Old traces have no revision (empty), not backfilled.
